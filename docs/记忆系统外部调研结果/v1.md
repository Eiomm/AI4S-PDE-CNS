| 出处 / 项目                               | GitHub 链接                                            | 具体思想                                                                                                                                                                                           | 对我们 Task1 的启发                                                                                                                                                            |
| ------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **MLEvolve**                          | InternScience/MLEvolve ([GitHub][1])                 | 用 **Monte Carlo Graph Search + multi-agent collaboration** 自动做 ML 竞赛搜索；它的 memory 记录每个 node 的 plan、code、metric、success/failure，并用 **BM25 + FAISS** 检索历史经验，帮助 planner 强化有效策略、避免已知坑。([GitHub][1]) | 这是最贴近我们 Task1 的。Task1 应该把每次实验都记录成 node：`改了什么 → 跑了多久 → RelL2 多少 → 是否合规 → 是否失败`。然后让 Agent 根据历史实验继续改 FNO/loss/scheduler，而不是每轮重新瞎试。                                          |
| **ML-Master 2.0 / HCC**               | sjtu-sai-agents/ML-Master ([GitHub][2])              | 提出 **Hierarchical Cognitive Caching, HCC**，把 transient execution traces 动态蒸馏成 stable long-term knowledge，让短期执行和长期策略解耦但共同演化。([GitHub][2])                                                       | 我们可以把 Task1 memory 分成三层：`Evolving Experience` 记录每轮 run，`Refined Knowledge` 保存验证过的 finding，`Prior Wisdom` 保存稳定策略，比如“不要用其他 Nu checkpoint”“先小样本搜索再全量复训”。                    |
| **A-MEM**                             | agiresearch/A-mem ([GitHub][3])                      | 借鉴 **Zettelkasten**，每条 memory 不是孤立文本，而是带 context、keywords、tags 的 note；新 memory 会和历史 memory 建立链接，并触发旧 memory 更新。([GitHub][3])                                                                   | Task1 的实验不能只存一行 log。比如“gradient loss 有效”“rollout loss 变慢”“width=128 OOM”要被链接到同一个主题：`loss_design / stability / resource_risk`。这样 Agent 检索时能看到一组相关经验。                      |
| **MemoryOS**                          | BAI-LAB/MemoryOS ([GitHub][4])                       | 把 memory 当成 OS 管理问题，包含 **Storage、Updating、Retrieval、Generation** 四个模块，并采用 short-term / mid-term / long-term hierarchical storage。([GitHub][4])                                                 | 我们可以做一个简化版 memory OS：`working/current_context.json` 管当前实验，`episodic/runs.jsonl` 管历史实验，`findings/*.yaml` 管验证发现，`wisdom/strategy_summary.md` 管长期策略。                        |
| **MemOS**                             | MemTensor/MemOS ([GitHub][5])                        | 强调统一的 memory API：add / retrieve / edit / delete；memory 不是黑盒 embedding store，而是可检查、可编辑的 graph；支持多模态、tool traces、多个 memory cube。([GitHub][5])                                                    | Task1 的 memory 必须可审计。每条 finding 要有 evidence、run_id、metric、适用条件、置信度，不能只存一句“gradient loss 好用”。尤其赛题有合规要求，memory 必须能追溯来源。                                                    |
| **MemP / Procedural Memory**          | zjunlp/MemP ([GitHub][6])                            | 把过去 agent trajectory 蒸馏成两类 procedural memory：细粒度 step-by-step instruction 和高层 script-like abstraction；并支持 build、retrieval、update、deprecate。([GitHub][6])                                       | Task1 非常需要 procedural memory：如何加载 FNO checkpoint、如何按 `reduced_resolution_t=5` 降采样、如何生成 `task1_pred.hdf5`、如何跑 evaluator。这些应该沉淀成 `memory/procedures/*.md`，让 Agent 每次照流程执行。 |
| **Reflective Memory Management, RMM** | 论文为主，未看到官方 GitHub；ACL 2025 paper                     | 提出 prospective reflection 和 retrospective reflection：前者把历史交互按粒度总结进 memory bank；后者根据模型实际引用的 evidence 反过来优化 retrieval。                                                                           | Task1 里 retrieval 也要被评估。如果 Agent 检索到“加大 width 有效”，结果导致 OOM，那这次检索应被记录为 harmful retrieval，并给这条 memory 降权或加 caveat：`only works with smaller batch`。                         |
| **Graphiti / Zep Temporal KG**        | getzep/graphiti ([GitHub][7])                        | 用 temporal context graph 管理 agent memory。每个 fact 有时间有效区间、provenance，并支持 semantic + keyword + graph traversal 的 hybrid retrieval。([GitHub][7])                                                  | Task1 的实验结论会随阶段变化：小样本有效不等于全量有效，20 epoch 有效不等于 500 epoch 有效。可以借鉴 temporal KG：每条 finding 要记录“何时成立、在哪个 split/epoch/seed 成立、是否被后续实验推翻”。                                      |
| **Mem0**                              | mem0ai/mem0 ([GitHub][8])                            | 生产级 memory layer，强调 user/session/agent 多层 memory、entity linking、multi-signal retrieval：semantic、BM25 keyword、entity matching 并行融合。([GitHub][8])                                                | 我们可以用类似 multi-signal retrieval：查实验时不能只靠 embedding，还要支持按 `model=FNO`、`loss=gradient`、`status=OOM`、`relative_l2 < baseline` 精确过滤。也就是 embedding + metadata SQL/CSV 检索。      |
| **SimpleMem**                         | aiming-lab/SimpleMem ([GitHub][9])                   | 非常朴素的三步：store information、index memory、retrieve relevant memory；把信息转成 structured atomic memories，再用 embedding + metadata 组织。([GitHub][9])                                                      | 适合我们先做 MVP。不要一开始做复杂图数据库。先做 `runs.jsonl + validated_findings.yaml + failure_bank.yaml + memory_retrieve.py`，能跑起来最重要。                                                      |
| **Awesome-Memory-for-Agents**         | TsinghuaC3I/Awesome-Memory-for-Agents ([GitHub][10]) | 它把 agent memory 分成 short-term 和 long-term；long-term 又区分是否依赖任务成败结果，特别提出 **Experience** 是由任务 outcome 验证过的知识。([GitHub][10])                                                                       | Task1 的 memory 最应该是 experience-driven。不要保存“LLM觉得可能有效”的想法，只有跑过 evaluator、有 metric、有 success/failure 的实验，才能进入 experience memory。                                           |
